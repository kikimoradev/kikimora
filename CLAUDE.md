# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`brownie` — a CLI (Node >= 22, pnpm, ESM, TypeScript, npm package `@brownie-labs/brownie`, binary `brownie`) that cyclically runs Claude Code sessions in a two-agent setup: the **monitor** reports tasks, the **executor** completes them, and the **summarizer** writes findings to long-term memory. Code, messages, and commits are in English.

Like Claude Code's `.claude/`, all per-project state lives in `<cwd>/.brownie/`: `settings.json` (configuration), `prompts/*.prompt.md` (project prompts), `data/` (tasks.json, memory.db, mcp/, playwright/), `logs/` (session logs), `.gitignore` (self-ignores data/ and logs/). System prompts ship with the package (`<packageRoot>/prompts/*.system.md`). Agent sessions run in the project directory itself (`cwd`), not in a sandbox. The full path layout is defined in `src/paths.ts` (`projectPaths`, `packagePromptsDir`, `systemPromptFiles`).

## Commands

```bash
pnpm dev                  # start with watch (tsx)
pnpm start                # start without watch (first run opens the two-prompt wizard)
pnpm check                # typecheck + lint + format:check + test (run before committing)
pnpm typecheck
pnpm lint / pnpm lint:fix
pnpm format / pnpm format:check
pnpm test                 # vitest run
pnpm test test/executor.test.ts        # a single test file
pnpm vitest run -t "test name"         # a single test by name
pnpm test:coverage        # coverage thresholds enforced in vitest.config.ts
pnpm build                # tsup -> dist/
```

## Architecture

The entry point `src/index.ts` dispatches manually on `argv`: `brownie mcp …` goes to `mcpCommand` (`src/mcp-command.ts`, a citty group whose only subcommand `serve` is the memory MCP server), `brownie init` to `initCommand` (`src/init-command.ts` — non-interactive scaffolding through `src/scaffold.ts`, shared with the wizard; every input is read and `--settings` validated with `parseSettings` before the first file is written, and `--force` covers every file the call writes; without flags in a TTY it delegates to the wizard), `brownie status|version|pause|resume|drain|tasks|settings|prompt|memory` to the control commands (`src/control-commands.ts` and the `*-command.ts` groups, clients of the control socket), everything else to `mainCommand` (`src/main.ts`, citty; flags `--headless`, `--log-format pretty|json` with the `BROWNIE_LOG_FORMAT` env fallback, `--verbose`, `--paused` with `BROWNIE_START_PAUSED`). `runBrownie` in `main.ts` runs the first-run wizard (`runConfigure` in `configure.tsx`) only when the setup is missing (`isConfigured`: `.brownie/settings.json` + both project prompt files) — and only in a TTY — then starts the worker. The wizard is a small standalone Ink app (`src/ui/wizard.tsx` + the multi-line `src/ui/prompt-editor.tsx`, its own Ink instance unmounted before the dashboard mounts) that asks **only** for the two project prompts (Enter = newline, Ctrl+D = submit, Esc = cancel, pasted markdown is normalized); it writes `settings.json` as `{}` (zod defaults cover everything) and never overwrites an existing settings file. The manual dispatch exists because citty treats the first positional raw arg as a subcommand name and runs the parent `run` after a subcommand. Brownie always operates on `process.cwd()` — there is no flag to point it elsewhere (test code injects paths via the `ConfigDirs` object instead).

`src/start.ts` (`startWorker`) wires everything together: after preflight (`preflight.ts`) and loading the configuration, it runs **two loops in parallel** (`Promise.all`) that communicate only through shared objects:

- **`runMonitorLoop` (`monitor.ts`)** — every `intervalMs` (and only within the window from `active-hours.ts`) it fires a Claude session with an enforced task-report JSON schema (`report.ts`), adds tasks to the `TaskStore` (deduplicated by `id`), and wakes the executor via the `Waker`.
- **`runExecutorLoop` (`executor.ts`)** — pulls `pending` tasks from the `TaskStore`, appends the task description to the prompt, and runs a session with access to memory (MCP). Transient failures (`isTransientFailure`: a timeout or a pattern in the result text) are retried up to `maxTaskAttempts` with a delay; the rest are marked `failed`. After each session (success or failure) it fires the `SessionSummarizer`.

Both loops (and the summarizer) share a **`UsageLimitGate` (`usage-limit.ts`)** — resilience against Claude Code usage limits (5h/weekly). `detectUsageLimit` recognizes a limit hit in a `SessionResult`: structurally via the `rate_limit_event` stream event (`rate_limit_info.status === "rejected"`, captured by `stream.ts` into `SessionResult.rateLimit` with `resetsAt` unix seconds) with a text-pattern fallback for older CLI formats. On a hit the gate blocks both loops until `resetsAt` + 60s buffer (or a 15 min fallback when the reset time is unknown); each loop checks `gate.msRemaining()` at the top of its iteration and shows a `limitWait` phase with a countdown. The executor returns the task to the queue via `TaskStore.release` (status back to `pending`, the attempt is given back — limit hits never consume `maxTaskAttempts`) and skips the summarizer. Next to it sits the **`AuthGate` (`auth-gate.ts`)**: `detectAuthFailure` recognizes rejected credentials (`api_retry` stream events with `error_status` 401/403, captured by `stream.ts` into `SessionResult.apiError`, plus a text fallback) and must run **before** `detectUsageLimit` and `isTransientFailure`, whose `/API Error/` pattern would otherwise retry a 401. The gate is indefinite: `engage` pauses both `AgentController`s (callback wired in `start.ts`), the loops report the `authBlocked` phase once and park in `controller.gate()`, and any `resume` clears it via the controllers' `onChange`. Both gates travel as `LoopGates` (`gates.ts`). Preflight also runs `claude --version` and `claude auth status --json` once (both handed to `start.ts` as `PreflightResult.claude`) and refuses to start without a login (older CLIs only warn).

Each loop also gets an **`AgentController` (`control.ts`)** — the pause/resume primitive behind `/pause` and `/start`. `pause()` marks the state `pausing` (the running session finishes), the loop's `gate(signal)` call at the top of each iteration flips it to `paused` and blocks until `resume()` or abort; `controller.sleep()` wraps `timing.ts` `sleep` so pause requests cut sleeps short. Abort always wins and resolves everything (same convention as `Waker`/`sleep`: resolve, never reject). In an interactive terminal `start.ts` constructs the controllers as `paused` — agents only run after the user types `/start`; without a TTY (no way to type commands) they boot `running` unless `--paused` (or `BROWNIE_START_PAUSED=1`) asks for a paused start.

**`DrainController` (`drain.ts`)** turns the pause primitive into a graceful exit (`brownie drain`, the `drain` socket command, `/drain`). `request(reason, timeoutMs)` records a `DrainSnapshot`, announces it (`worker.draining`, `WorkerStatusStore.drainRequested`), pauses both controllers and arms an unref'd deadline; `start.ts` calls `noteSettled` from both controllers' `onChange`, and the moment both are `paused` — both loops parked in `gate()`, so no session and no summary is in flight — it aborts. The deadline aborts regardless, killing what still runs. A second `request` returns the first snapshot and never moves the deadline, and `resume` is refused while draining (socket and `/start`), because a resumed loop would pass its gate once more. The worker's single `AbortSignal` is `AbortSignal.any` of the signal handler's and the drain's, and `worker.stopped` reports `drained` and, unless the drain `settled`, `forced`.

Other pieces:

- **`runner.ts`** — the only place that spawns the `claude` process (`-p --model --effort --system-prompt --output-format stream-json --permission-mode bypassPermissions --mcp-config --strict-mcp-config`, prompt via stdin). Handles timeout/abort (SIGTERM, then SIGKILL after 5s). `stream.ts` parses stream-json into `SessionEvent`s and builds a `SessionSummary`.
- **`tasks.ts` (`TaskStore`)** — a JSON task store (`.brownie/data/tasks.json`), atomic writes (tmp + rename), operations serialized through a promise chain; on startup it resets stalled `in_progress` tasks back to `pending`.
- **`src/memory/`** — long-term memory: `store.ts` (SQLite via `node:sqlite` + FTS5), `summarizer.ts` (a haiku session that reads the executor session log, writing the result to the database), `mcp.ts` (a stdio MCP server with the `memory_search`/`memory_get` tools, reached by pointing an MCP config back at the same binary: `brownie mcp serve --db ...`).
- **`mcp-config.ts`** — the MCP configuration handed to every session. `composeMcpConfig` builds the document: `memory` first (executor only — `memoryDbPath` is `null` for the monitor, and the summarizer gets nothing), then `playwright` when `browser: true` (`playwright-mcp`, headless, isolated profile, `--output-dir .brownie/data/playwright`; preflight checks the binary is on `PATH`), then the servers the agent's `mcpServers` list names, copied verbatim from `settings.mcpServers`. `writeMcpConfig` writes it atomically to `.brownie/data/mcp/<agent>.json` and returns the path; both loops and the summarizer call it at the top of an iteration, the same rhythm that re-reads the prompt files, so a settings change applies to the next session. `runner.ts` **always** passes `--mcp-config <path> --strict-mcp-config`, even for an empty document: an agent sees exactly the servers in `settings.json` and never a `.mcp.json` from the repository (untrusted input) or the user's own Claude Code configuration. Reserved server names (`memory`, `playwright`) and references to undeclared servers are rejected by `settingsSchema`.
- **`src/headless/`** — headless mode, active without a TTY or with `--headless`: `start.ts` then skips `mountDashboard` entirely and tees line logs to stdout instead. `tee.ts` (`teeReporter`) fans out **every** reporter method (unlike `teeSession`, which tees only the `session` sink) into `reporters.ts` — implementations of `MonitorReporter`/`ExecutorReporter`/`SummaryReporter` that map lifecycle callbacks to `HeadlessLogEvent`s (`events.ts`); `format.ts` renders them as pretty lines or NDJSON (stable envelope `ts`/`level`/`agent`/`event` + fields, undefined fields omitted — the schema is documented in `docs/deployment.md`), `sink.ts` writes to stdout (injectable via `StartWorkerOptions.stdout` in tests). Session `text`/`toolUse`/`toolResult` events are logged only with `--verbose`. The `WorkerStatusStore` keeps running headless because it feeds the control socket.
- **`control-server.ts` / `control-client.ts` / `control-protocol.ts` / `control-commands.ts`** — the control socket: a unix domain socket (named pipe on win32) at `controlSocketPath(projectDir)` (`paths.ts`: tmpdir + uid + sha256 of the resolved project path — deliberately outside `.brownie/` to stay under the ~104-byte `sun_path` limit; `BROWNIE_CONTROL_SOCKET` overrides it, validated in the same function so the worker and the CLI agree). `start.ts` always starts the server (both TUI and headless); startup probes the socket first — a live listener means another instance and the worker exits 1 with "already running (pid …)", a stale file is unlinked. Protocol: one newline-delimited JSON request per connection, validated by the zod discriminated union `controlRequestSchema`, answered with `{ok:true,data}` / `{ok:false,error}` typed per command (`ControlResponseData`). Besides `status`/`version`/`pause`/`resume`/`drain` it mirrors the TUI — `settings.get|patch`, `tasks.list|add|retry|cancel`, `memory.search|recent`, `prompt.get|set` — so the server gets the same store instances as the dashboard through the neutral interfaces in `worker-controls.ts` (never import `src/ui/` there). `version` answers the static `WorkerIdentity` (`worker-identity.ts`: brownie/Claude Code/Node versions, pid, `startedAt`, `projectDir`, and `authKind` resolved as `ANTHROPIC_API_KEY` → `CLAUDE_CODE_OAUTH_TOKEN` → the preflight `claude auth status` report, matching Claude Code's own precedence), built once in `start.ts`, spread into the `status` document and logged in the headless `worker.started` event; protocol fields are only ever added, never renamed or nulled (optional ones are omitted). The CLI side (`brownie status|version|pause|resume|drain` and the `*-command.ts` groups) goes through `requestControl` in `control-commands.ts` and exits 1 when no worker answers or the request is rejected — an `Unrecognized control request.` from an older worker is reported as a version skew with a restart hint.
- **`src/sessions/`** — `SessionIndex`, the durable index of every session brownie has run. It shares `MemoryStore`'s single writable `node:sqlite` handle (`memory.connection`), owns the `sessions` table in `.brownie/data/memory.db`, and is fed by `runner.ts` through the narrow `SessionRecorder` port: `started` on the `init` event (the only place the session id is known for certain — `result` may never arrive), `finished` when the process ends. `start.ts` builds one recorder per agent, turning `SessionLog.pathsFor(sessionId)` into paths relative to `.brownie/` so the index stays valid on both sides of a bind mount. `sessions.list`/`sessions.get` and `brownie sessions` read it; neither ever returns transcript content.
- **`status.ts` + `src/ui/`** — `WorkerStatusStore` collects events from both loops (phases, tails, control state, recent outcomes) and feeds the TUI (Ink/React). The TUI is a Claude-Code-style shell: `app.tsx` holds the **single `useInput` hook per Ink instance** (never add a second one in the dashboard — Ink delivers every keypress to all active subscribers; the wizard is a separate, sequential Ink instance with its own `useInput` in `prompt-editor.tsx`), the view router, the input state, and the layout math; `commands.ts` is the pure slash-command registry (`COMMANDS`, `parseCommand`, `suggest`, `dispatchCommand`) — one source of truth for `/help` and tab completion, handlers talk to narrow structural interfaces (`TaskControls`, `MemoryReader`, `SettingsController`), never to concrete stores; views live in `src/ui/views/`, presentational pieces in `command-input.tsx`/`agent-panel.tsx`/`task-table.tsx`, colors in `theme.ts` (single brand-green accent `#4CAF50`). The dashboard mounts only in an interactive terminal — without a TTY (or with `--headless`) `start.ts` never calls `mountDashboard` and the headless line logger takes over. `/exit` and ctrl+c both go through `process.kill(pid, "SIGINT")` → `abortOnSignals` — the only immediate shutdown path; `/drain` goes through the `DrainController`. Session events are simultaneously tee-d (`teeSession`) into persistent `SessionLog` files (`.brownie/logs/<agent>/<day>/<HH-MM-SS>-<sessionId>.log` for people, `.jsonl` next to it for machines).
- **`settings-controller.ts` + `settings-file.ts`** — runtime configuration changes behind the `/model`, `/effort`, `/interval`, `/hours`, `/days` commands (and the `/config` view). `patchSettings` (settings-file) applies a sparse patch to the raw `settings.json` JSON, validates it with `settingsSchema` **before** writing (tmp + rename), and returns the parsed `Settings`; `createSettingsController` (built in `start.ts`, passed to the TUI) validates the value, persists via `patchSettings`, then calls `applySettings(config, settings)` which **mutates the shared `WorkerConfig` leaves in place** — never reassign `config.monitor`/`config.executor`/`config.summarizer`, because `monitor.ts`/`executor.ts` hold destructured references to those sub-objects and read `model`/`effort`/`intervalMs`/`schedule` per iteration; that is what makes changes apply to the next session without a restart. `promptPath` stays restart-only. Project prompts are edited in place with `/prompt <monitor|executor>`: the command reads the file via `prompt-files.ts` (`PromptFileAccess`, atomic tmp+rename writes) and opens `PromptEditor` as a modal view — while it is mounted the dashboard's main `useInput` is deactivated (`isActive`), so the editor is the only key subscriber; saving needs no live-apply because both loops re-read the prompt files every iteration.
- **`paths.ts`** — the single source of truth for the filesystem layout: `projectPaths(projectDir)` derives every `.brownie/` path, `packageRootDir`/`packagePromptsDir` locate the installed package via `import.meta.url` (works both in dev via tsx and in the tsup bundle `dist/index.js`).
- **`config.ts`** — all configuration in `.brownie/settings.json`, a nested JSON validated with zod (`settingsSchema`, `.strict()` at every level, so typo keys fail with a named path). A new configuration option = a key in `settingsSchema` + a mapping in `loadWorkerConfig` + a leaf assignment in `applySettings` (`settings-controller.ts`) + usually a slash command in `src/ui/commands.ts`. `ConfigDirs { projectDir?, systemPromptsDir? }` exists for test injection; production code always passes `{}`.

## Prompts

All agent prompts live in markdown files. **Never put prompt content as constants in the code** — always in markdown files.

The **system prompts** (`prompts/*.system.md`) ship with the npm package (listed in `package.json` `files`) and resolve from the package root, not from the user's project; they are in English and impose no output language. The **project prompts** (`.brownie/prompts/monitor.prompt.md`, `.brownie/prompts/executor.prompt.md`) are written by the wizard into the user's project and carry the business context (Redmine IDs, repositories, URLs).

## Tests

- Vitest, tests in `test/` mirror the structure of `src/`. Coverage thresholds (statements 92%, lines 94%…) are enforced in `vitest.config.ts` — new code must be tested.
- Claude sessions are tested without a real CLI: `test/fixtures/claude` is a fake binary script driven by `FAKE_CLAUDE_*` variables (mode, result text, argument dump), with per-model variants via the `_<MODEL>` suffix. Helper factories for configs and reporters are in `test/helpers.ts`.

## Documentation

- Every user-facing change lands in `CHANGELOG.md` under `## [Unreleased]` (Keep a Changelog: `Added` / `Changed` / `Fixed`, one dense bullet per change, written for the user, not the diff).
- Each doc owns one topic and stays terse: `README.md` is the overview and command tables, `docs/configuration.md` settings, `docs/prompts.md` prompts, `docs/deployment.md` headless mode and servers, `docs/control.md` the control socket (CLI, containers, wire protocol). A feature that touches several topics gets one sentence with a link in each, not a copy of the explanation — prefer a short paragraph or a table row over a new section, and a new file over a section that mixes audiences.

## Conventions

- ESLint: `strictTypeChecked` + `stylisticTypeChecked`; `tsconfig` with `exactOptionalPropertyTypes` (hence explicit `| undefined` in interfaces).
- User-facing messages, CLI descriptions, errors, and commits in English; no comments in the code.
- Agent sessions run in the project directory itself (`config.cwd = process.cwd()`); `.brownie/` is runtime state (gitignored in this repo and ignored by eslint) — not part of the source code.
